# 재점검 명령서 — 배포한 수정이 운영에서 실제로 되는지 확인

배포할 때마다 이 명령서를 씁니다. 재점검 #2(1~3단계 이후), #3(4~5단계 이후) 모두 같습니다.
`====` 로 둘러싼 부분만 복사해서 수정 세션에 붙이세요.

## 소유자용 안내

- **왜 매번 하는가.** 로컬에서 되는 것과 운영에서 되는 것은 다릅니다. 특히 음성 클립은
  R2 에 따로 올려야 하므로, 텍스트만 배포되면 학습자는 **눌러도 소리가 안 나는 버튼**을 만납니다.
- **누가 하는가.** 고친 세션이 자기 작업을 검사합니다. 그래서 명령서가 "확인했습니다" 대신
  **숫자**를 요구하도록 돼 있습니다. 판정은 숫자를 보고 사장님이 하시는 겁니다.
- **겹쳐 돌리지 마세요.** 이 컴퓨터는 메모리 7.9GB 라 브라우저 작업 2~3개가 한계입니다.

====================== 여기서부터 복사 ======================

운영(https://k-ig-core.vercel.app)에서 이번에 배포한 수정이 실제로 되는지 확인해라.

지금부터 검사하는 건 네가 고친 것들이다. 네가 네 작업을 검사하는 것이므로
"확인했습니다" 라고 쓰지 마라. 숫자만 내놔라. 판단은 사장이 한다.

■ 지킬 것
  유료 강의는 이미 등록된 감사용 프로필을 그대로 써라. 새 기기를 등록하지 마라.
  이용권 코드·비밀번호·관리자 PIN 을 타이핑하지 마라.
  /api/license/ 중 상태를 바꾸는 것과 /api/admin/ 의 변경 계열을 부르지 마라.
  CNN · GVA 는 폐지 과정이다. 건드리지 마라.
  진도·북마크를 바꿨으면 전부 H.logDataChange 로 남겨라.
  고치지 마라. 이번에는 확인만 한다. 문제를 찾으면 보고하고 멈춰라.

■ 1. 이번에 새로 만든 음성 클립이 운영에서 실제로 소리가 나는가
  파일이 있는지가 아니다. 앱이 요청하는 바로 그 주소로 200 이 오고,
  Content-Type 이 audio/mpeg 이고, 바이트 수가 로컬 파일과 같은지 확인해라.
  유료 클립은 이용권 세션이 있어야 받아진다. 로그인 상태로 해라.
  표로: 강의 / 문장 / HTTP 상태 / 운영 바이트 / 로컬 바이트 / 일치 여부
  하나라도 200 이 아니면 거기서 멈추고 보고해라. R2 업로드가 빠진 것이다.

■ 2. 이번에 글자를 바꾼 강의가 운영 화면에 반영됐는가
  바꾼 문장이 실제로 화면에 새 내용으로 나오는지, 강의를 열어 확인해라.
  바꾼 강의 전부다. 표본이 아니다.

■ 3. 이번에 고친 기능이 운영에서 동작하는가
  고친 항목마다 학습자가 실제로 하는 동작을 그대로 해보고 숫자로 보고해라.
  예: 채점 고친 것은 직접 타이핑해서 정답 처리되는지, 검색 고친 것은
  실제로 검색어를 넣어 몇 건이 나오는지.
  6단계가 말하기 채점기(src/lib/speechRecognition.ts — 6-1274 줄표·따옴표, 6N-001 줄임말)를 고친
  배포에서는 **휴대폰 실제 마이크로** — 헤드리스 브라우저는 마이크가 없어 이것을 못 한다:
    ① READING pr083 발음 시험 문장을 또박또박 읽어 90점 이상 (고치기 전 함수로는 완벽히 읽어도 55)
    ② STUDENT s1-3 "I'm a pretty happy person." 을 "I'm …" 과 "I am …" 으로 두 번 읽어 둘 다 90점 이상
       (고치기 전 함수 86 · 31, 고친 뒤 100 · 100)
  사람이 휴대폰으로 해야 하는 항목이라 결과 표에 누가 언제 했는지 적어라.
  7단계 배포에서는 이것도(숫자로):
    ① GRAMMAR 종합 평가에서 실제로 타이핑: 모범 "He is Japanese." 에 "He isn't Japanese." → 0점(뜻이 반대 — 소유자 결정
       2026-09-24) · "He is a Japanese." → 70점 · 모범 그대로 → 만점.
    ② LISTENING 받아쓰기 입력: d016 9:15 문장을 "nine fifteen" 으로 → 정답 · "ten fifteen" → 오답. 하이픈 낱말을 띄어 써서 → 정답.
    ③ 위 '전체 듣기': gh1-084 가 영어 답을 읽는가(BUG-026) · VOCA mv3-04 의 labo(u)r 가 소리 나는가(BUG-027) — 요청한 클립 키와 상태로.
    ④ 강의 첫 HTML 에 본문이 있는가(BUG-023 — 무료 5쪽 gh1-006 · d001 · pr001 · s1-1 · mv1-01 의 첫 응답에
       `<template id="B:0">` · `$RC` 가 없고 본문 글이 있음) · 소리를 켠 채 다음 강의로 넘어가면 소리가 멈추는가(LessonSpeechGuard).
    ⑤ 속도(BUG-023): 이용권 프로필 · 휴대폰 4G 로 강의 쪽 LCP — 9/22 기록 3.3초와 나란히.
    ⑥ 7단계 수정 파일에 재기용 스위치(KIG_MEASURE_OLD_LESSON_BODY 등)가 남지 않았는가 — 배포한 커밋에서 grep 0.
  BUG-018(이용권 저장 방식)은 7단계와 따로 배포한다. 그 배포 뒤에는 소유자-이용권-시험지.md 10번(기존 사용자 전환)을
  소유자가 보고, 이 명령서의 5번(잠금 · 무료)을 다시 돌린다.

■ 4. 고치지 않은 부분이 망가지지 않았는가
  이번 수정이 건드린 과정의 강의를 drive-generic.cjs 로 전부 돌려라.
  표본이 아니라 전부다. 콘솔 오류 수, 실패한 단계 수, 빈 화면 수를 숫자로.

■ 5. 유료 잠금이 그대로인가
  로그아웃 상태에서 유료 주소가 여전히 잠기는지, 무료 28개는 여전히 열리는지.
  숫자로: 잠긴 유료 주소 N개 / 열린 무료 주소 N개.
  ※ 접근 제어를 건드린 배포에서는 이 항목을 절대 건너뛰지 마라.
    무료 강의를 막아버리는 사고가 가장 나기 쉬운 곳이다.
  무료 강의는 **소리까지** 로그아웃 상태로 확인해라 — 먼저 node docs/qa-2026-09-18/scripts/audio-inventory.cjs
  로 목록을 지금 내용으로 새로 만들고(옛 목록이면 가짜 경보), 그다음 node docs/qa-2026-09-18/scripts/audio-check.cjs --anon
  → 무료 강의 클립 전부 200/206 audio, 유료 클립 전부 403. 숫자로: 무료 클립 N/N · 유료 403 N/N.
  무료 강의(d001 · d002 등)의 문장이 바뀐 배포는 배포 전에 node scripts/buildFreeSpeechKeys.mjs --check 가
  exit 0 인지부터 — 목록이 낡으면 이용권 있는 점검은 통과하는데 체험하러 온 사람만 그 문장 소리가 막힌다.

■ 보고 형식
  항목마다 "몇 개 중 몇 개" 로 써라. 전부 통과면 그것도 숫자로 써라.
  실패가 하나라도 있으면 제일 위에 써라. 밑에 묻지 마라.

====================== 여기까지 복사 ======================

- **음성 1번이 실패**하면 R2 업로드가 빠진 것입니다. 클립을 올린 뒤 다시 확인합니다.
- **5번에서 무료 28개가 안 열리면** 즉시 되돌려야 합니다. 돈 낸 사람이 아니라
  체험하러 온 사람이 막히는 것이라, 매출이 그대로 사라집니다.
